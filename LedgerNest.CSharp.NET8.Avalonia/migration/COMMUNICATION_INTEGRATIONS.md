# Communication integrations

## Discovery and implementation

The desktop app persists invoices through MainWindowViewModel.SaveInvoice. New
invoices become Unpaid immediately; there is no separate finalization command.
Quotations, receipts, drafts, deleted documents and voided invoices are excluded
from customer delivery. Payment and void hooks run after database commit.

The existing DocumentPdf pipeline and saved document export context supply invoice
PDFs. A single generated byte array supplies all requested customer channels.
No public PDF hosting or separate rendering engine is introduced.

Implementation order: domain contracts and configuration; application dispatcher;
protected infrastructure persistence and real provider adapters; existing settings
shell and consent UI; invoice/event hooks and desktop worker; reports, history,
retry/recovery and verification.

### Responsibilities

* Domain/Communication.cs: provider contracts, configuration, consent, payload and history.
* Application/CommunicationDispatcher.cs: template validation, recipient validation,
  consent/status enforcement, duplicate prevention and retry coordination.
* Infrastructure/CommunicationStore.cs: existing EF settings repository, DPAPI,
  persistent outbox claims and reports over actual invoices/payments.
* Infrastructure/CommunicationProviders.cs: SMTP, official Meta Graph API and
  Telegram Bot API adapters. HttpClient is injected for HTTP tests.
* Desktop/CommunicationSettingsViewModel.cs and Views/CommunicationSettingsView:
  configuration, masked credential replacement, consent, tests, preview and history.
* Desktop/MainWindowViewModel.Communication.cs: composition, saved-document PDF
  delivery and worker/report coordination. MainWindow owns the 30-second polling
  timer and shutdown cancellation.

All channels default off. Provider failures do not roll back invoices or payments.
No new library, external server or service-locator dependency is required.

## Persistence / upgrade / backups

No invoice or customer schema is changed. Existing settings keys and values remain
untouched. The new versioned namespace uses the existing settings primary key:

* communication:v1:configuration -- encrypted configuration including credentials.
* communication:v1:consent:{customerId} -- encrypted explicit channel consent,
  Telegram verification, recording user and timestamp.
* communication:v1:job:{SHA256(deduplicationKey)} -- encrypted history and retry state.
* communication:v1:payload:{SHA256(deduplicationKey)} -- encrypted message/PDF.
  History reads metadata only; the worker loads a payload after claiming a job.

Existing databases need no DDL migration: missing keys mean disabled defaults.
The settings primary key enforces enqueue uniqueness. A conditional SQL UPDATE
claims each job only if its stored value is unchanged. This works with the existing
EF database factories; SQLite is covered by the integration tests.

Normal whole-database backup/restore carries these records. DPAPI uses the current
Windows user (not machine-wide encryption). Restoring under another Windows
account cannot decrypt communication records: reconfigure communication using the
original Windows account/profile or a separately provisioned new database. Never
copy credentials into plaintext to work around that restriction. Non-Windows
credential storage is deliberately unsupported; disabled integrations still work.
Protect database backups as business data. There is no automatic history deletion;
history filters display the latest 500 jobs. Plan retention for large PDF volumes.

## Configuration

Sign in as Admin with Settings Update permission. Open Settings > Communication.
Each channel has independent Enabled, test, reset and event preferences. Save
Configuration persists all sections using the existing settings action bar.
Reset is staged until Save. Saved secrets always render as blank password fields;
blank retains the saved credential. Reset + Save clears a credential.

An integration with pending work cannot be disabled without selecting the explicit
pause confirmation. Disabled channels are checked again before every attempt.

### Email

Use your provider's SMTP host, sender, username/app password and submission port,
usually 587 with STARTTLS. This adapter uses .NET SmtpClient and supports STARTTLS
and unauthenticated None; implicit TLS/SMTPS on port 465 is not supported. Plain
authentication is rejected. TLS certificates use normal system validation.
Reply-To and display name are optional. Timeouts are bounded to 5–120 seconds.

Test Connection checks the SMTP greeting only. Send Test Message validates the
full TLS/authentication/send flow and attaches a clearly labeled test PDF.
SMTP acceptance is recorded as Sent, never as confirmed delivery.

### WhatsApp Business Platform

Only official Meta Cloud API is supported; the HTTPS host is fixed to
graph.facebook.com to prevent sending credentials to arbitrary configured hosts.
Provide an approved business account, registered Phone Number ID, appropriate
access token and a currently supported Graph API version (enter it explicitly).
Configure country code, template names and language. Media is uploaded through
/{version}/{phone-id}/media and sent by media ID in a template document header.

Create and obtain approval for:

1. Invoice template: optional DOCUMENT header (required when Send PDF is enabled);
   body parameters in order: customer name, invoice number, company, amount, date.
2. Separate administrator template: no document header; body parameters in order:
   event name, report/event text. Set Admin Template Name separately.

Template names, parameter counts, language and document-header configuration must
match Meta approval exactly. Local free-form text never bypasses template approval.
Meta account permissions, restrictions and messaging limits remain authoritative.
Changing Send PDF requires a matching approved template. Test uses the invoice
template and a test PDF; no real invoice/customer data is used.

Record customer opt-in before enabling WhatsApp consent. Enter a single number
with international country code; a 10-digit local number uses Default Country Code.
Administrator destinations must also be consented before configuring them.

Official references:
https://developers.facebook.com/docs/whatsapp/cloud-api/
https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/messages/document/
https://whatsappbusiness.com/blog/manage-message-templates-whatsapp-business-api/

### Telegram

Create a bot through BotFather. Enter its token, administrator Chat ID and test
Chat ID. The user must start the bot or add it to the destination group with
permission to post. Test Connection uses getMe and, when a test destination is
provided, getChat. A successful check retrieves the bot username.

PDF delivery uses multipart sendDocument; text uses sendMessage. Plain text and
safe HTML headings are supported. Customer/company values are HTML-escaped.
Overlong captions/text fail clearly instead of silently truncating reports.
See https://core.telegram.org/bots/api#getme and
https://core.telegram.org/bots/api#senddocument.

Telegram customer delivery requires explicit opt-in AND Verify Telegram Destination
followed by Save Customer Consent. Reachability verification does not replace
obtaining customer consent or checking the identity of the destination.

## Customer delivery and history

Record consent against a saved customer in Communication settings. Email/phone
remain managed in the existing Customer screen. Enable automatic delivery if
desired. The invoice success screen offers Email, WhatsApp, Both and Resend Invoice.
Invoice View + Update permission is required; disabled and unconsented channels
are skipped. Invalid contact information fails validation.

Initial delivery keys are unique per invoice/channel. Repeated initial clicks do
not resend. Explicit resend creates a new key. A queued payload is the saved PDF
at the time of queuing; resending a history entry repeats that payload. Use the
invoice screen's Resend Invoice to generate from the current saved document.
Missing/invalid contact details are logged per channel; they do not block other
valid channels in a multi-channel request. Fix the contact and use Resend Invoice.

History includes recipient, IDs, channel, event, timestamps, attempts, provider ID,
status and safe errors. Sent means submitted/accepted; no webhook delivery
confirmation is implemented and no Delivered claim is made.

Check provider history and select the authorization checkbox before Retry Failed
or Resend Submitted. Invoice status and current consent are checked again before
sending, including retries. Draft/void/deleted invoices cancel pending delivery.

Only explicit provider rejection known safe to retry (HTTP 429, selected SMTP
temporary rejection codes) receives exponential backoff or provider Retry-After.
Provider pauses apply across that channel even when automatic retries are disabled.
Paused channels do not hold up independent enabled channels. Administrator event
preferences and destinations are rechecked before sending; changed destinations
cancel queued messages rather than delivering data to the former administrator.
Unknown network outcomes are NOT automatically repeated. Processing jobs older
than five minutes become Failed with an uncertain-delivery explanation after
restart. Interrupted/timeout sends may have reached the provider; review first.
Without provider idempotency/webhooks, exactly-once external delivery cannot be
guaranteed across a crash after acceptance. The outbox deliberately favors avoiding
duplicates over automatically repeating uncertain requests.

## Administrator reports and events

Per-channel preferences cover new/finalized invoice, void, payment, overdue,
delivery success/failure, integration failure and daily/weekly reports. Overdue
checks use saved snapshot due dates and actual outstanding amounts, once per local
day. Drafts, voids, deleted invoices and invoices without a saved due date are excluded.
New and finalized are separate selectable notifications at the same save boundary.

The desktop checks every 30 seconds while open and signed in. Daily reports cover
the previous local calendar day; weekly reports cover the prior Monday–Sunday.
They queue once per period/channel, including when the app reopens after a
scheduled boundary. This is a desktop scheduler, not an always-running server:
it does not send while the application is closed, and does not backfill every
historical period missed during a long closure.

Reports use persisted invoices/payments, current customer counts and real outbox
results. Voided invoices are excluded from monetary totals. Amounts, top customers,
trends and payment-method summaries remain separated by saved invoice currency;
legacy records without currency are explicitly labeled Unspecified. Paid and
outstanding against period invoices are their current balances, not reconstructed
historical end-of-day balances. No unavailable historical metrics are invented.
Invoice counts use invoice date, not an invented creation timestamp. Delivery
counts use actual submission/attempt dates and exclude administrator/test messages.

## Verification and external prerequisites

Automated tests use isolated SQLite databases, a local loopback SMTP server and
mocked HTTP/provider results. They never contact real customer destinations.
UI tests render the existing Settings shell in narrow/light and desktop/dark modes,
checking layout, credential masking, save preservation and authorization.

Build and test commands/results are recorded in the task's final report. Live
SMTP/Meta/Telegram accounts and approved test destinations were not supplied.
Before enabling production channels, an administrator must run the explicit
connection and test-message actions using their own test accounts, confirm sender
permissions/template approval/bot access, and verify actual receipt. This cannot
be validated by compilation or mocked tests.
